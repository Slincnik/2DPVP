# ADR-0001: клиентский 2D-фреймворк

- **Статус:** принято
- **Дата:** 2026-09-17

## Контекст

Клиент дуэли должен работать с авторитетной серверной симуляцией, иметь
собственный фиксированный simulation tick и без ограничений встраивать
QUIC-клиент, prediction и reconciliation в игровой цикл.

## Решение

Для MVP используем **raylib** как тонкий клиентский фреймворк. Исходный код
клиента остаётся C++, а raylib используется только для окна, ввода, 2D-рендера
и аудио. Игровая симуляция, сетевой код и игровой цикл принадлежат проекту.

Начальная структура клиента:

```text
client/
  app/        # точка входа и render loop
  platform/   # адаптер над raylib: окно, ввод, отрисовка
  game/       # локальное представление дуэли и UI
  net/        # QUIC, протокол, prediction/reconciliation
```

Simulation loop использует accumulator и фиксированный шаг `1/30 s`;
рендеринг выполняется с независимой частотой. `SetTargetFPS` не является
механизмом синхронизации симуляции.

## Альтернативы

- **SFML:** подходящий и зрелый вариант, но для MVP даёт больше API, чем
  требуется, без преимуществ для сетевого цикла.
- **SDL3 напрямую:** максимальный контроль, но требует самостоятельно
  строить больше слоя платформы и рендера.
- **Cocos2d-x:** не выбран: последняя стабильная ветка устарела, а сам проект
  рекомендует Cocos Creator для новых проектов.

## Последствия

- Лицензия raylib (zlib/libpng) совместима с коммерческим распространением.
- Фреймворк не определяет архитектуру игры: заменить его позже можно через
  `client/platform`.
- Для сборки клиента потребуется CMake; зависимость raylib будет закреплена
  через FetchContent или пакетный менеджер после выбора целевых платформ.
