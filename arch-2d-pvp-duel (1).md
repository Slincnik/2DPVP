# Архитектура: 2D Realtime PvP Duel

Дуэльная 2D-арена, 1v1, живые игроки в реальном времени.
Клиент/движок: C++. Бэкенд: Go. Транспорт игровых тиков: QUIC (datagram-режим).

---

## 1. Общая схема

```
┌─────────────────┐        QUIC (TLS1.3)        ┌──────────────────────┐
│   C++ Client     │ ───────────────────────────▶│   Go Match Server     │
│  (engine + UI)   │◀─────────────────────────── │  (per-room goroutine) │
└─────────────────┘   datagram: input/state      └──────────────────────┘
        │              stream: hit/death/chat               │
        │ HTTPS/gRPC (login, mm, profile)                    │
        ▼                                                    ▼
┌──────────────────────┐                         ┌──────────────────────┐
│   Go API Gateway      │────────────────────────▶│  Postgres / Redis     │
│ (auth, matchmaking,   │                         │ (профили, рейтинг,    │
│  profile, leaderboard)│                         │  очередь мэтчмейкинга)│
└──────────────────────┘                         └──────────────────────┘
```

Два разных Go-сервиса на старте можно даже объединить в один бинарник (монолит), просто с чёткими внутренними модулями — разделять на микросервисы будет несложно позже.

## 2. Компоненты

### 2.1 Go API Gateway (HTTP/gRPC, не realtime)
Отвечает за всё, что не требует низкой задержки:
- **Auth**: регистрация/логин, выдача JWT.
- **Profile**: ник, уровень, статистика.
- **Matchmaking queue**: игрок встаёт в очередь → сервис ищет пару по рейтингу → создаёт матч на Match Server → возвращает обоим клиентам адрес/токен для подключения к комнате.
- **Leaderboard**: топ игроков.
- **Post-match**: приём результата, обновление ELO (если сервер матча не делает это сам).

Хранилище: Postgres (профили, рейтинг, история матчей), Redis (очередь мэтчмейкинга, presence, кэш).

### 2.2 Go Match Server (realtime, QUIC)
- **MatchManager** — создаёт/уничтожает комнаты (`Room`) по запросу от Gateway.
- **Room** (goroutine на каждую активную дуэль):
  - Держит авторитетное состояние обоих игроков (позиция, HP, кулдауны атак).
  - Тикает с фиксированной частотой (например 30 или 60 Hz).
  - Каждый тик: читает буфер накопленных инпутов от обоих клиентов → применяет к состоянию → считает столкновения/урон → рассылает snapshot обоим.
  - Конец матча (HP=0 / таймаут) → шлёт результат в Gateway (по внутреннему gRPC/каналу), закрывает комнату.
- **Транспорт**:
  - QUIC datagram (ненадёжно, без порядка) — для инпутов игрока и снапшотов состояния каждый тик.
  - QUIC reliable stream (в том же соединении) — для редких критичных событий: старт/конец матча, урон/смерть, чат, дисконнект.

### 2.3 C++ Client
- **Network layer**: QUIC-клиент (например через `msquic` или `quiche` — нужно выбрать C++-совместимую QUIC-библиотеку с datagram-поддержкой).
- **Input**: сбор ввода каждый локальный кадр, упаковка и отправка на сервер с номером тика.
- **Client-side prediction**: локально сразу применяет своё же движение, чтобы не было ощущения задержки — сервер потом присылает авторитетную позицию, клиент **реконсилирует** (плавно поправляет), если разошлось.
- **Interpolation** для противника: сглаживание между полученными снапшотами (обычно рендерят с небольшой задержкой ~100мс от "настоящего времени" сервера, буферизуя 2-3 снапшота).
- **Rendering/engine loop**: как в обычном твоём движке, только с добавленным сетевым слоем и рендером состояния, приходящего от сервера, а не только локальной симуляции.

## 3. Формат данных

Рекомендация: **Protobuf** для всех сообщений (клиент↔gateway и клиент↔match server) — есть кодогенерация и под C++, и под Go, компактный бинарный формат, легко версионировать.

Примерные сообщения:

```protobuf
// Клиент -> Match Server, каждый тик (datagram)
message PlayerInput {
  uint32 tick = 1;
  float move_x = 2;
  float move_y = 3;
  bool attack = 4;
  bool jump = 5;
}

// Match Server -> оба клиента, каждый тик (datagram)
message WorldSnapshot {
  uint32 server_tick = 1;
  PlayerState player_a = 2;
  PlayerState player_b = 3;
}

message PlayerState {
  float x = 1;
  float y = 2;
  int32 hp = 3;
  uint32 last_acked_input_tick = 4; // для реконсиляции на клиенте
}

// Reliable stream события
message MatchEvent {
  oneof event {
    MatchStart start = 1;
    HitEvent hit = 2;
    MatchEnd end = 3;
    ChatMessage chat = 4;
  }
}
```

## 4. Матчмейкинг — минимальный флоу для MVP

1. Клиент → Gateway: `POST /queue/join` (с JWT).
2. Gateway кладёт игрока в очередь Redis (ZSET по рейтингу).
3. Фоновый воркер каждые N мс сканирует очередь, ищет пары в пределах ±X рейтинга.
4. Найдена пара → Gateway просит MatchManager поднять `Room`, получает адрес/порт + одноразовый токен для каждого игрока.
5. Оба клиента получают `{server_addr, port, match_token}` через long-poll/WebSocket/повторный запрос `GET /queue/status`.
6. Клиенты подключаются к Match Server по QUIC, предъявляя token → Room аутентифицирует и стартует матч, когда оба на месте.

Для MVP можно вообще без Redis — держать очередь в памяти одного процесса Gateway, это упростит первую версию.

---

## 5. Античит / авторитетность

- Сервер — единственный источник истины по хитбоксам, урону и результату.
- Клиент никогда не шлёт "я нанёс урон" — только ввод. Сервер сам решает, было ли попадание.
- Fixed timestep на сервере и одинаковая логика симуляции — если когда-то понадобится детерминированный replay/спектейт.

## 6. Структура репозитория — монорепо

Клиент (C++) и бэкенд (Go) живут в одном репозитории. Разные тулчейны друг другу не мешают — просто соседние папки. Единый `proto/` в корне — общий источник правды, никакой синхронизации между репозиториями не нужно.

```
game-monorepo/
├── proto/                      # .proto файлы — source of truth для клиента и бэка
│
├── client/                     # C++ клиент/движок
│   ├── engine/                 # выбранный движок или обёртка над ним (см. раздел 9)
│   ├── net/                    # QUIC-клиент, (de)serialization, prediction/reconciliation
│   ├── proto/                  # сгенерированный C++ код из proto/
│   └── game/                   # логика дуэльного режима поверх engine + net
│
├── backend/                    # Go: gateway + match server
│   ├── cmd/
│   │   ├── gateway/main.go
│   │   └── matchserver/main.go
│   ├── internal/
│   │   ├── auth/
│   │   ├── matchmaking/
│   │   ├── room/                # игровая логика матча (Room, тик-луп)
│   │   ├── proto/                # сгенерированный Go-код из proto/
│   │   └── storage/              # postgres/redis обёртки
│   └── go.mod
│
├── deploy/
│   └── docker-compose.yml      # postgres + redis + gateway + matchserver
│
├── Makefile                    # make proto / make backend / make client / make dev
└── README.md
```

**Что нужно на старте, кроме структуры папок:**
- Единая цель кодогенерации протобаф — например, `make proto`, которая гоняет `protoc`/`buf` и кладёт результат в `client/proto/` и `backend/internal/proto/` за один запуск.
- CI (когда дойдёт до этого) — отдельные джобы для Go и C++, но триггерятся одним пушем в монорепо; тулчейны не пересекаются, конфликтов не будет.
- Для соло-разработки версионирование клиента и бэка отдельно друг от друга не требуется — оба деплоятся/собираются из одного коммита, это даже упрощает жизнь.

## 7. Дорожная карта для агента (по фазам, каждая — рабочий инкремент)

**Фаза 0 — Skeleton**
- Поднять go.mod, структуру папок, protobuf-компиляцию (buf или protoc) для Go и C++.
- Gateway: `/health`, простой in-memory auth-заглушка (без реальной верификации паролей).

**Фаза 1 — Одиночная комната без сети**
- В Go: реализовать `Room` и тик-луп полностью изолированно, с юнит-тестами (два "фейковых" инпут-потока → детерминированный результат).
- Это позволяет проверить игровую логику дуэли, не трогая сеть вообще.

**Фаза 2 — Сетевой каркас**
- QUIC-сервер в Go (без datagram пока, обычный reliable stream, для простоты первой версии).
- Минимальный QUIC-клиент в C++, который может подключиться, отправить фейковый инпут и получить снапшот — просто чтобы прогнать пайплайн end-to-end.

**Фаза 3 — Datagram + client prediction**
- Перевести инпуты/снапшоты на QUIC datagram.
- Добавить client-side prediction и reconciliation на клиенте.
- Добавить interpolation для отображения противника.

**Фаза 4 — Матчмейкинг и Gateway**
- Очередь (сначала in-memory), поиск пары, выдача токена, связка с Match Server.
- Postgres: профили, история матчей, ELO после `MatchEnd`.

**Фаза 5 — Полировка**
- Reconnect после потери соединения.
- Таймауты/afk-детект.
- Chat/social события через reliable stream.
- Leaderboard endpoint.

Каждую фазу можно отдавать агенту как отдельную задачу с чётким критерием "готово" (например: "тесты Room проходят", "клиент видит движение оппонента с сервера").

## 8. Что нужно решить/выбрать до старта

- **QUIC-библиотека для C++**: `msquic` (Microsoft) или `quiche` (Cloudflare) — обе поддерживают datagram extension, стоит сравнить сложность интеграции под твою систему сборки.
- **Частота тика**: 30 Hz обычно достаточно для 2D-дуэли (не шутер с хитскан-оружием), проще для старта, можно поднять позже.
- **Protobuf vs свой бинарный формат**: protobuf проще для итерации, свой формат — чуть меньше оверхед. Для MVP — однозначно protobuf.

---

## 9. Важно: своего C++ движка пока нет

В предыдущих версиях этого документа предполагалось, что клиент строится поверх уже существующего собственного движка. **Это не так** — собственного 2D-движка на C++ на данный момент нет, и весь раздел про `client/engine/` в разделе 6 нужно рассматривать как открытый вопрос, а не готовую базу.

Это отдельная задача, которую агент должен решить **до** написания сетевого слоя (`client/net/`) и игровой логики (`client/game/`), потому что от выбора зависит структура папки `client/`.

**Что нужно сделать агенту на этом этапе:**
1. Сравнить готовые 2D-движки/фреймворки под C++ по критериям: простота интеграции своего сетевого кода (QUIC-клиент + кастомный game loop с фиксированным тайм-степом), лицензия, активность поддержки, кроссплатформенность (если нужна), сложность сборки рядом с Go-частью монорепо.
2. Кандидаты, которые обычно рассматривают для такого сценария (агенту стоит проверить актуальное состояние каждого, а не полагаться на устаревшие данные):
   - **raylib** — минималистичный, простой C API, легко встроить свой game loop и сетевой слой, малый оверхед.
   - **SFML** — чуть более высокоуровневый, C++-идиоматичный, хорошая экосистема.
   - **Cocos2d-x** — полноценный игровой движок с редактором и готовыми абстракциями (сцены, ноды, физика), но тяжелее и более "своё мнение" о структуре проекта — может конфликтовать с кастомным сетевым тик-лупом.
   - **SDL2/SDL3 напрямую** — не движок, а низкоуровневая библиотека (окно, ввод, рендер, звук); даёт максимум контроля над game loop, но больше писать самому (по сути "собрать свой движок", только быстрее, чем с нуля).
3. Дать рекомендацию с обоснованием, отталкиваясь от того, что критично для этого проекта — **полный контроль над фиксированным тайм-степом и вставкой сетевого кода в цикл**, а не богатство готовых игровых абстракций.
4. Только после выбора — наполнять `client/engine/` (либо как обёртку над выбранной библиотекой, либо напрямую использовать её API из `client/game/`).

Если раньше в голове держался пункт "движок уже есть, дуэльный режим пишется поверх него" — теперь это часть Фазы 0/1 дорожной карты (раздел 7), а не готовая предпосылка.
